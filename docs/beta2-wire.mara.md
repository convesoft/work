# Beta.2 wire specification

This is the normative format and operation specification refined by [[DES-BETA2-WIRE]]. It specifies **planned** beta.2 behavior, not the behavior of the installed alpha or the current beta.1 source. Acceptance of this document is a knowledge gate, not runtime, package, integration or publication evidence. [Scope ownership](scopes.mara.md), [scoped execution](scoped-execution.mara.md), [item format](item-format.mara.md), and [template format](template-format.mara.md) supply the preserved semantics. The [closed schema catalog](schemas/beta2-wire-v2.schema.json) specifies decoded new envelopes, tool inputs and result shapes. This document supplies framing, cross-file invariants, grammar, authorization, publication ordering and retry rules that JSON Schema cannot express.

## Incremental implementation and evidence

The full catalog is the final beta.2 contract. Bounded delivery advertises only implemented CLI/MCP operations with their frozen schemas, never placeholder tools. Hosting/material routing may be verified through real public calls against prepared, validated version-2 execution records; that proves validation, routing and byte/identity preservation, not downstream run/session/claim lifecycle, relocation or disposal workflows. Those remain combined/downstream gates. The onboarding contract is [[DES-REPOSITORY-ONBOARDING]].

## 1. Common types and framing

`ID` means a generated UUIDv4 encoded as 32 lowercase hexadecimal characters (version nibble 4, variant nibble 8–b). All persisted references and results use full IDs. Creation retries collisions without overwrite. `ScopeID` is an item ID or the literal `root`, reserved for the virtual repository root within this Git repository. An item-rooted stored scope uses **the material item's ID**, not a second identity. Wisps cannot establish run or hosting boundaries: promote first. Implicit wisp scopes and ordinary parentage remain valid.

`ItemRef` accepts a full ID or an unambiguous lowercase hex prefix, optionally prefixed by `w-`; a prefix has 1–31 digits, and a full ID has 32. Raw inspection/repair require full IDs. Entity references (runs, claims, session records, handoffs, progress records) require full IDs, never prefixes. `ScopeRef` is `root` or an ItemRef, including an implicit material scope. Stored child references always use full non-root ScopeIDs.

`Name` is the case-sensitive **session-name** type `[A-Za-z][A-Za-z0-9_.-]{0,63}`. `TemplateIdentifier` is the preserved `[a-z][a-z0-9_]*` type with **no length limit**, used for template names, parameter/existing-binding keys and local item keys. `TemplateEndpoint` is `root`, `local:<TemplateIdentifier>` or `existing:<TemplateIdentifier>`. Malformed template filename summaries retain the raw name string with diagnostics, not a falsely valid identifier. A session selector is exactly `NAME` or `RUN_ID/NAME`; slash occurs only as that separator. Qualification selects an exact immutable run, not its scope's replacement round. `Text` is a nonblank single-line UTF-8 string. `External` is `{namespace:string,id:string}`, both nonempty opaque UTF-8 strings, case-sensitive and not trimmed or delimiter-parsed. Actor is Text: a supplied label, not an authenticated principal. `Time` is UTC RFC3339 with `Z`; Work generates lifecycle times (Observation.observed_at is explicitly caller-supplied), never uses timestamp order for authority or expiry. `Hash` is lowercase SHA-256 hex. `Path` is an absolute Unix path encoded bytewise: preserve ASCII alphanumerics and `/._-`, percent-encode every other byte with uppercase hex, decode exactly once. CLI path arguments are ordinary OS paths; MCP path strings and all emitted paths use Path. `RelPath` uses safe project-relative components, no empty, `.` or `..` components, no leading slash or backslash; generated entity paths must match this layout, not arbitrary caller paths.

All **new** decoded file envelopes have `format_version: 2`. This intentionally distinguishes them from obsolete version-1 execution envelopes; material items stay version 1 and templates retain versions 1 and 2. New YAML is one UTF-8 mapping without BOM, using the JSON-compatible YAML 1.2 subset. Reject duplicate/unknown keys, aliases, anchors, merge keys, tags, extra documents, wrong types and explicit null except the required nullable TreePlan.parent_before/parent_after fields. Optional file/input keys are omitted, never null; defaults are only those stated. A future/obsolete version yields `unsupported_format` before interpreting fields. Missing/malformed fields at version 2 yield `invalid_format`. No migration or rewriting on read occurs. Output nulls are explicitly specified below and in the catalog. Output schemas are the beta.2 baseline; callers may ignore future additive output keys but must not reinterpret existing ones. Input and file schemas are closed.

Handoffs and digests use the item format's exact `---` frontmatter framing, LF/CRLF delimiter acceptance and opaque bytes after the closing delimiter's line ending. Body is UTF-8, including empty text, leading blanks and final-newline choice. No body headings, links, checklists, summaries or outcome classifications are parsed. Item envelope/body rules remain [[DES-ITEM-FORMAT]] unchanged.

## 2. Storage, authority and lifetime

Let `C` be the authoritative hosting checkout, `G` the actual Git common directory, and `D` a checkout's actual Git metadata directory resolved through Git. Never assume `.git` is a directory. Git's worktree inventory identifies the primary checkout (even detached or on any branch). A bare/non-Git directory is `unsupported_project`. Ordinary working repositories with a primary .git directory, their linked .git-file checkouts and detached primary checkouts are supported. git init --separate-git-dir is explicitly unsupported and returns unsupported_project without writes; do not substitute its administrative path, add a locator or install configuration. Separate clones and remote coordination are outside scope.

| Record | Exact location | Authority and lifetime |
| --- | --- | --- |
| Material item | `C/.work/items/<item-id>.md` | Whole file selected by nearest host; recorded item lifecycle, body and relations; independent of execution disposal |
| Template | Selected checkout's `.work/templates/<name>.yaml` | Versioned reusable definition; no execution initialization needed for material planning |
| Scope anchor | `C/.work/scopes/<scope-id>/scope.yaml` | Stable explicit boundary and run selection; retained while run history/children or dedicated material hosting require it |
| Child reference | Parent anchor host's `.work/scopes/<parent-scope-id>/children/<child-scope-id>.yaml` | One parent-local tree edge to next stored boundary; not an item parent assertion or a global registry |
| Run | `C/.work/scopes/<scope-id>/runs/<run-id>/run.yaml` | Exactly one owning scope/storage home, mutable phase, no member list or checkout paths |
| Wisp | Same run directory's `items/<item-id>.md` | Version-1 item envelope; containing run owns lifetime even after later execution rounds; committing is not promotion |
| Named session | Same run directory's `sessions/<record-id>.yaml` | Immutable name/identity plus lifecycle/observations; retained terminal identity until explicit disposal |
| Claim acquisition | Same run directory's `claims/<claim-id>.yaml` | Immutable acquisition; sole unended acquisition across authoritative homes establishes repository-wide item ownership |
| Claim ending | Same run directory's `claims/<claim-id>.end.yaml` | Immutable single ending; acquisition/end retained until owning run disposal |
| Handoff | Same sending run directory's `handoffs/<handoff-id>.md` | Immutable sender-local context; recipient state never controls retention |
| Digest | Material root host's `.work/digests/<root-id>/<run-id>.md`; virtual-root digest uses `root` | Exact supplied extension, no Work item/lifecycle; survives execution disposal |
| Host declaration | `D/work-beta2-hosts.yaml` | Machine-local **dedicated hosting overrides only**, not run phases, ancestry or item copies |
| Coordination | `G/work-beta2/coordination.lock` | Empty stable OS advisory-lock target, not an entity registry, owner PID or generation store |
| Host-transfer progress | `G/work-beta2/relocations/<operation-id>.yaml` | Narrow machine-local declaration-transfer intent, removed after completion |
| Other progress | `C/.work/scopes/<scope-id>/progress/<kind>/<operation-id>.yaml` | Versionable bounded start/ending/rotation/promotion/disposal intent; removed after completion; no generic operation service |

`kind` in the last path is exactly `start`, `ending`, `rotation`, `promotion` or `disposal`. Hidden same-directory stages and displaced-source copies are never live entities. All Work-managed publication, including scope-owned records and Git-local hosting/progress files, follows [[DES-FILE-PUBLICATION-LIFECYCLE]]: verified ordinary writes clean obsolete artifacts, while unknown or unresolved recovery content remains inspectable until explicit resolution. This does not prune authoritative records or evidence still needed by an unfinished continuation. No shared global runs/claims/sessions/handoffs/workspaces directories, authoritative lookup database, required persistent global index, receipts, automatic ignoring of authoritative records/progress or custom Git refs exist. Explicit init installs only the fixed housekeeping rules in [[DES-REPOSITORY-ONBOARDING]]. Readers build disposable maps from parent-local anchors, Git inventory and declarations, then parse authoritative files under coordination. Unknown non-hidden entries, missing expected files, symlinks/nonregular entity files, duplicate IDs and malformed ownership are diagnostics, not empty state. Unreferenced scope/run directories are diagnosed as orphan/interrupted content, not activated.

### 2.1 Exact source envelopes

The catalog's named `$defs` are normative decoded schemas. Fields below are exhaustive; `?` denotes optional omission. ID/path equality with containing directories is mandatory. ID sets are distinct and sorted lexicographically on write; arrays with publication order retain that order.

| Schema | Exact fields and constraints |
| --- | --- |
| `ScopeAnchor` | `format_version:2`, `scope_id:ScopeID`, `execution:ExecutionBoundary`. No parent/host/branch/path/member copies |
| `ExecutionBoundary` | Exactly `{mode:"uninitialized"}` at root before explicit execution initialization, `{mode:"inherit"}` at non-root, `{mode:"boundary",run_id:ID}` selecting an active or retained terminal run, or `{mode:"ended",run_id:ID}` at non-root after the selected terminal run is disposed. Ended is a namespace barrier, not a reference requiring the deleted manifest. Root cannot inherit or use ended; initialized root never loses its selected round without replacement |
| `ChildReference` | `format_version:2`, `child_scope_id:ID`. Parent is the containing directory; child's scope ID equals its material root ID |
| `HostDeclaration` | `format_version:2`, `scope_ids:ID[]` (possibly empty). Root is prohibited: primary hosting is a Git fact. An absent declaration means no dedicated overrides, not an unavailable initialized scope |
| `RunManifest` | `format_version:2`, `id:ID`, `created_at:Time`, `phase:"active"|"finalized"|"abandoned"`; terminal requires `ended_at:Time`, active prohibits it. `summary_sha256?:Hash` only on finalized when a digest was supplied. Owning scope/root/home are derived from path, not duplicated |
| `NamedSession` | `format_version:2`, `id:ID`, `name:Name`, `actor:Text`, `identity:External`, `registered_at:Time`, `state:"active"|"retiring"|"retired"`, `retirement_requested_at?:Time`, `retired_at?:Time`, `observation?:Observation`. Active prohibits retirement fields; retiring requires requested time only; retired requires retired time and may retain requested time. Name/ID/tuple/time immutable |
| `Observation` | `availability:"available"|"unavailable"|"unknown"`, `observed_at:Time`, `note?:string`. Caller-supplied observation, no polling, lifecycle, claim release or process-control effect |
| `ClaimAcquisition` | `format_version:2`, `id:ID`, `item_id:ID`, `actor:Text`, `identity:External`, `acquired_at:Time`, `named_session?:SessionAddress`. No workspace, generation, mutable owner or duplicated home |
| `SessionAddress` | `run_id:ID`, `session_record_id:ID`. Exact immutable record; captured actor/identity in an acquisition must match it, even for cross-run uses |
| `ClaimEnding` | `format_version:2`, `claim_id:ID`, `ended_at:Time`, `ended_by:Text`, `reason:string` (ordinary release/completion default empty), `outcome:"released"|"completed"|"reassigned"`, `recovery?:true`. Recovery requires nonblank reason; ending must match the containing acquisition. No inferred replacement acquisition |
| `HandoffHeader` | `format_version:2`, `id:ID`, `created_at:Time`, `from_items:ID[]` (possibly empty for a run-level report), `destinations:Destination[]` (nonempty, distinct), `sender?:SenderIdentity`. Sending run/scope derives from path |
| `SenderIdentity` | `actor:Text`, `identity:External`, `named_session?:SessionAddress`. Snapshot, not a rebindable alias |
| `Destination` | Exactly `{kind:"item",item_id:ID,validated_run_id?:ID}`, `{kind:"run",run_id:ID}` or `{kind:"session",run_id:ID,session_record_id:ID}`. Item's optional authored qualification is provenance, **not** a recipient-round filter |
| `DigestHeader` | `format_version:2`, `root_scope_id:ScopeID`, `run_id:ID`. Path equality required; body is supplied summary. No digest ID or parsed result |

A parent-local child reference connects a stored child to the nearest stored ancestor dictated by current material item parentage (virtual root when none). Every non-root anchor has exactly one such incoming reference. Anchors exist only for run/hosting boundaries and required retained history, not every item. Creating/reparenting a boundary updates this tree under the same lock using the bounded start/tree-update rules below. Synthetic item edges are prohibited. Run-only boundaries inherit host routing; only `HostDeclaration.scope_ids` establish dedicated overrides. Thus parent relocation carries inherited child anchors/runs but leaves explicitly hosted descendants in place. A hosting-only anchor remains after execution disposal while material source routing requires it.

The primary root is derivable before any files exist. Ordinary material CRUD may establish coordination/checkout locks without initializing execution. Explicit hosting may create a root anchor with uninitialized execution. Explicit work init alone establishes the default run. Fresh material writes prepare only required planning directories/locks after input/candidate validation; absent catalogs read as empty without writes. Init also prepares the primary checkout's required directories and fixed housekeeping .gitignore rules; it does not edit every linked branch. Never recreate a missing coordination lock automatically when persisted execution/progress exists; report `coordination_unavailable`. Creating a fresh lock uses exclusive safe publication and verifies the held pathname/inode. Its existence alone is not execution initialization.

### 2.2 Resolution and physical inspection

Start at the primary root, traverse parent-local references, apply nearest dedicated host override and load whole material files from that host, including uncommitted bytes. Validate the authoritative material ancestry and scope tree together; never mix another copy's header with the selected body's bytes. Include retained wisp files for graph/reference inspection; old wisps retain their original owner run regardless of later material ancestry. Sibling graph references resolve across hosts. Merely merging files does not add a declaration, select a current run or acquire ownership.

Missing/ambiguous/unreadable authority returns diagnostics and `HostCandidate` records wherever discoverable. No newest-copy rule, branch-name preference, stale fallback or automatic authority change is allowed. Read-only `view:"physical"` reads the selected checkout's `.work` files only and reports `authoritative:false`; it may inspect otherwise inactive scope/run copies without activating them. It never supplies execution authorization. Every mutation rejects a physical view before any write. Machine callers resolve ambiguity with `scope_select_authority`, not a TUI. If an old host/source is unreadable, **transfer is refused until it is recovered for comparison**; even stopped-executor attestation and a plausible copy do not establish continuity. This wire-review safety choice is canonical in [[DES-SCOPE-TRANSITIONS]].

## 3. Execution, identity and authorization

### 3.1 One-home runs and derived state

For a material item, nearest boundary in stored/implicit ancestry determines effective run. A retained ended boundary returns that exact terminal run plus `execution_state:"ended"`, never ancestor fallback. After explicit disposal, its `mode:"ended"` anchor retains the barrier and former ID but returns null effective run; fresh start or explicit inheritance resumption is still required. No boundary before initialization returns null run and `uninitialized`. For a wisp, `owner_run_id` always identifies its containing run. A current wisp's ancestry must select that same active run; a retained terminal wisp is historical and never joins replacement rounds.

At most one run is selected at a boundary. Active selected runs are current; historical active or unselected manifests are an invalid/interrupted state, not competing current runs. A dedicated checkout alone does not make a new namespace. Start creates a fresh ID only at a material scope lacking an active selected run; same current start is unchanged. Starting/resuming inheritance refuses any current claims on material/wisp items whose effective context would change. `run inherit` is non-root only, clears the ended boundary to inherit (or is unchanged if already inheriting), keeps history and dedicated hosting, and requires a healthy active inherited context. It cannot silently end an active own run. Old wisps remain historical.

`members` of an active run are material descendants with that effective run plus current owned wisps, **including its material root as context**. `required_members` excludes the owning material root; virtual root has no item. No attach/detach/member list exists. Required membership includes material obligations and active descendant-run wisps across nearer child boundaries for the parent's completion calculation; exclude retained terminal wisps from replacement rounds, but do not hide unfinished current child subtrees by filtering to the parent's execution namespace. Report both `members` and `required_members` so context and obligation sets are not conflated. `finished` for a non-root active run requires a nonempty required set, all effective done under the preserved graph, no claims on those obligations or root, and no current claims of its named identities in any run. Finalization additionally requires descendant runs ended. Recorded root completion stays independent. For the virtual-root run and retained terminal runs `finished` is null, not a recomputation that rewrites historical success after later material edits.

Root rotation does not require repository-wide material completion or nonempty members. It requires no claims in the root execution/affected obligations, drained root-session cross-run claims and ended descendants. It refuses any unfinished owned root wisps unless `abandon_unfinished:true`; that choice ends the old round as abandoned, otherwise finalized. Keep open abandoned wisps/history; never mark them/material work done. Rotation establishes a fresh active root round with a new ID and empty owned execution records. Root cannot be ended with ordinary finalize/abandon/inherit calls; rotation is its ending path.

Terminal execution permits historical reads, explicit unclaimed promotion and explicit disposal only. Ordinary wisp create/update/repair/reopen/close/relation mutation, new ownership and new outgoing handoffs are rejected as `run_not_current`. Material editing/lifecycle remains independent, but acquiring its execution requires active effective context. Incoming context may still be read from retained ended senders. All run endings refuse relevant current claims and every cross-run claim referencing a session owned by that run, then retire idle active/retiring names before terminal publication. Ending never releases claims.

### 3.2 Session namespaces and ownership forms

Registration requires an active run. One immutable run-local name maps to one generated record/tuple. Identical registration returns `changed:false` with the existing record without resetting lifecycle/observations. Different tuple under a used name is `session_conflict`, including retired names. No reuse/rebind/rename/remove operation exists. `session_retire` serializes with acquisition: active becomes retiring immediately; when all claims referencing the record anywhere drain, it becomes retired. Existing owner completion/release/outgoing handoff remains valid while retiring. Retired names cannot acquire or originate messages; terminal history is retained. A repeated retirement is unchanged once already in the requested/drained state. Availability changes never advance lifecycle; `session_observe` replaces only Observation, even on a retained terminal record.

`AcquireIdentity` is exactly one of `{session:SessionSelector}` or `{actor:Text,identity:External}`. Resolve a bare name in a single operation context. Acquire an item: its effective run. Claim-next: explicit `run_id` or effective run of `scope` (default root). Bare-name claim-next intersects selection with **that one run**, before choosing candidates. Never resolve the same name separately among candidate runs. Qualified name permits broader ordinary selection, while its named record still must be active. A named identity may claim work in another active run; the claim lives in the item's effective run and references the name's immutable owning run/record.

`OwnerIdentity` for a one-item owner operation is exactly `{session:SessionSelector,claim_id?:ID}` or `{identity:External,claim_id:ID}`. Actor is unnecessary for an existing explicit owner. Under the same held lock, name-only form resolves and matches the current acquisition of the target item. Exact `claim_id` fences a particular acquisition and rejects stale/mismatched pairs. Name-only intentionally means current matching ownership, not a stale acquisition fence. No identity is an authentication secret.

`Authorization` for multi-source edits is an array of `{item:ItemRef,session:SessionSelector,claim_id?:ID}` or `{item:ItemRef,identity:External,claim_id:ID}`; default empty. Each changed source with a current claim needs matching authorization. Unclaimed sources need none; supplied stale/unused/duplicate authorization fails, never silently ignored. For one-item mutations, top-level OwnerIdentity is shorthand for that item; reject mixing it with nonempty authorization. Relation changes authorize the actual authored file, including either existing author for symmetric removal, not every referenced target. Parent changes additionally refuse **all** affected claims whose effective context would change, even if the parent-file author is authorized. Wisp cross-run reparenting is rejected before publication (promote first). Nested-run creation applies the same context guard.

### 3.3 Claim invariants and stopped-executor actions

Current means one valid acquisition with no matching ending, across all authoritative run homes, not the newest timestamp. Multiple acquisitions, dangling/mismatched ends, invalid identity snapshots or unreadable records are `claim_conflict`/format diagnostics and block ownership-dependent mutations. Ended acquisitions are immutable history; references to disposed items/recipient sessions in history are audit facts, not deletion blockers. Ordinary release/recovery does not require the claimed item's missing/invalid source or graph to become valid; readable claim/home/identity and certain repository-wide exclusion are still required.

Acquire/reassign/next require valid entire resolved graph, active effective run and eligible open manual item, preserved inherited prerequisites, no current owner. Ready listing reserves nothing. Claim-next sorts priority ascending then full ID; empty eligible selection is `{claim:null,item:null,changed:false}`, distinct from corruption, source loss, ambiguity or contention. Root/run/scope/label/priority/persistence filters intersect candidate membership only, never remove outside prerequisites from graph evaluation.

Release writes an immutable `released` ending, then persists retirement of any now-drained retiring named identity (including a name owned by another run). Completion/recovery/reassignment apply the same post-ending drain check before returning success; ending a run retires its own idle names even if they were still active. A failed session-state publication is an error with the already-published ending in partial evidence, not a current claim. The caller may explicitly retire that exact named identity; exact-ID release may also finish its still-pending drained retirement when replayed. Repeated exact-ID release by the same identity with an already released ending and satisfied retirement postconditions is unchanged. Other ended outcomes/stale current pairs fail. Completing a claimed item saves outgoing handoffs, then item done state, then a completed ending. The still-current owner can retry an already-done item to finish its ending, without rewriting body/state or resubmitting saved messages. Name-only release with no current matching claim is stale, not a fabricated unchanged ending.

Recovery requires full claim ID, controller actor, nonblank reason and `executors_stopped:true`; it publishes a recovered released ending without completion. Reassignment additionally supplies AcquireIdentity, validates replacement eligibility first, ends old claim as reassigned, then creates a new immutable acquisition under one lock. Failure between writes leaves an inspectable ownerless gap. Repeating the old reassignment is stale; inspect then acquire if appropriate. No timer, restart, availability, retirement or stopped attestation itself releases/transfers anything. Work does not stop executors.

### 3.4 Sender-local messages and pull context

Handoff creation selects an active sending run explicitly with `run_id`, or from nonempty `from_items` when all share one effective active run; supplying both requires agreement. All `from_items` must resolve into that run; terminal wisps cannot originate context. A run-level report may have no items with explicit run. Optional AcquireIdentity captures sender identity; named retiring identity is allowed only for existing-owner operations/from_items it currently owns, never new acquisitions. Authorization covers every claimed source file/item represented as a sender. If sender identity is supplied, it must match each authorized claimed source owner; contradictory sender snapshots fail stale_claim. No identity creates a claim implicitly.

Input destinations are exactly `{kind:"item",item:ItemRef,run_id?:ID}`, `{kind:"run",run_id:ID}` or `{kind:"session",session:SessionSelector}`. Bare session destination is local to the sending run. Bare item destination is allowed only when its effective run equals sender; cross-run item requires explicit matching `run_id`. Run destinations always specify full immutable ID; cross-run session requires qualified selector. Target terminal run/session identities may receive a report while retained; they cannot send another report after ending. An item with no effective execution can be explicitly item-addressed without `run_id` only when sender is the standing root and item has no nearer ended boundary; otherwise invalid target/context is diagnosed. Resolve destinations before saving, canonicalize distinct destination tuples and preserve authored item qualification only as `validated_run_id` provenance.

Item incoming lookup matches stable `item_id` irrespective of its later run, hosting or material promotion. Run/session inbox matches exact IDs, never forwarding to replacements. Inspect/acquire returns full sender body/provenance and direct relation summaries; further neighbor bodies require another inspection. List/inbox filters sender run and/or one recipient, with AND semantics. Handoffs never add graph edges, alter readiness, push notifications, create read/unread state, acknowledgements or retention gates. Sender disposal deletes messages regardless of receiver/read state. Detectable missing/malformed sender files return `incoming_handoffs:null` plus diagnostics, never an empty successful lookup. Fully disposed senders have no persistent delivery tombstones, so absence is not proof of receipt.

## 4. Publication, interruption and bounded continuation

All cooperating reads hold shared repository coordination while resolving content; mutations hold exclusive coordination, then checkout locks in canonical absolute-path order. Reload, validate and recheck the entire captured source/host set (bytes, file identity, mode, directory identity and symlink destination) before publication; source changes fail `conflict`, including empty claim-next. Preserve the descriptor-bound safe-file safeguards in [[DES-DURABLE-OPERATIONS]]: restrictive staging, file/directory sync, no-overwrite creation and recoverable one-file replacement. [[DES-FILE-PUBLICATION-LIFECYCLE]] applies artifact cleanup to every publisher and caller, not only items; [[ADR-RECOVERY-ARTIFACT-LIFECYCLE]] records the project-wide retention trade-off. Cleanup failure after a verified save reports the affected published file/record, known partial progress and remaining artifacts through applicable publication/path fields; it must not imply an unpublished mutation, completed surrounding operation or safe automatic replay. Raw editors and external Git do not obey these locks; no cross-file atomicity, power-loss guarantee or transaction against such writers is promised.

Errors include `publication:not_published|possible|published` for the last attempted write and known `partial` progress; after `possible`, inspect the reported path before retrying. No error becomes success merely because an earlier step completed. Pending operation records freeze the exact target set; all ordinary mutations affecting it/its required graph or routing are rejected as `transition_pending`. Reads/diagnostics and the matching continuation remain available. No generic recovery tool, arbitrary path replay, cancellation/rollback service or permanent retry receipt is introduced.

### 4.1 Exact bounded progress envelopes

Every row additionally requires `format_version:2`, `id:ID` equal to filename, `created_at:Time`. `Snapshot` is exactly `{exists:false}` or `{exists:true,sha256:Hash}`. `FileMark` is `{path:RelPath,sha256:Hash}`; file byte length/mode/identity are rechecked in held live snapshots, not mistaken for portable identity. A plan's `step` is a nonnegative integer counting completed planned publication steps. After crash, reconcile only the next known step from its before/after hash; do not trust a stale step counter or infer broader success. Record publication may itself fail after its protected write: inspection compares expected before/after bytes.

`EndingPlan` has the fields listed for EndingProgress excluding `format_version,id,created_at`. `HostedInventory` is `{scope_ids:ScopeID[],files:FileMark[],sha256:Hash}`. Its hash is SHA-256 of UTF-8 JSON encoding of sorted `{scope_ids,files}` with those key orders and each FileMark's keys `path,sha256`, no whitespace/newline; include every material file routed by the transfer and every transferred anchor/child/run/progress/entity file, exclude dedicated descendants that stay hosted elsewhere and hidden recovery files. `AnchorChange` is `{scope_id:ScopeID,before:Snapshot,after:ScopeAnchor}`; disposal applies only exact planned execution-pointer changes, before deleting their selected terminal manifests. Ending plans capture timestamps/session sets at prevalidation; their step fields reconcile partial retirement, while outer disposal step covers the ordered deletion/pointer plan. Protected file hashes guard surviving references, including wisps outside the deletion set. `BoundaryCreation` is `{scope_id:ScopeID,checkout:Path,anchor_before:Snapshot,anchor_after:ScopeAnchor,parent_scope_id?:ScopeID,child_before?:Snapshot}`; parent/child fields appear together for non-root only. It creates only required new explicit boundary metadata (and an uninitialized root anchor if needed), not copied item/run data. Validate these exact new files in the prospective tree before intent publication. `DeclarationChange` is `{checkout:Path,before:Snapshot,before_scope_ids:ID[],after:HostDeclaration}`. The required before_scope_ids freezes the unique original declaration membership (empty for an absent before snapshot), independently of the snapshot hash; compare it with captured before bytes while those remain. Each declaration delta changes only the requested scope ID: add/retain it at the destination, remove it at recorded source checkouts, and preserve every other scope ID. Validate this before every publication/continuation, including when an earlier declaration is already installed; never infer the original membership from the after file. This user-approved clarification requires the field in externally prepared plans too. Compute a valid prospective scope/graph/claims view, not just a directory hash. Progress files themselves are excluded from their own inventory hash. Versionable progress stores no machine-local host facts; HostTransferProgress is nonversioned because it contains checkout paths/declarations.

Hosting-review clarification (user approved): inserting a hosting anchor above existing stored boundaries changes their nearest stored ancestor. `HostTreeReferenceChange` is exactly `{checkout:Path,parent_scope_id:ScopeID,child_scope_id:ID,before:Snapshot,after?:ChildReference}`. Omitted `after` means deletion; present `after` must identify that exact child. Freeze all required additional reference creations and superseded-reference removals in `HostTransferProgress.tree_references` before publication, including dedicated descendants whose hosts stay unchanged. Publish creations before destination declarations; remove superseded references after source declarations. The outer step counts every planned per-file publication. Continuation verifies completed steps, reconciles only the next step against its before/after bytes and never recomputes a broader target set. This supplies missing recovery bookkeeping for accepted implicit-ancestor hosting, not a new ownership model. Copies of inherited descendant anchors/run content must already be present and identical at the destination; Work does not copy them.

Runs/templates clarification (user approved): starting a non-root run at an implicit material ancestor of stored scopes must freeze the complete reference delta in StartProgress.tree_references, including its own incoming edge and every existing boundary whose nearest stored ancestor changes. The original parent_scope_id/child_before identify that incoming edge and must agree with the frozen delta. Publish the manifest first, reference creations in canonical parent/child order, selecting anchor, then superseded-reference removals in canonical order. The non-root step counts each planned file publication; root init retains its three-step form and prohibits tree_references. Continuation verifies all completed steps and reconciles only the next before/after bytes, preserving the exact generated run ID and the original reference set. It does not activate a manifest before its selecting anchor or recompute broader targets. This is start-specific scope-tree bookkeeping, not a generic journal or a host transfer.

A start/tree update may need both removal of the old parent-local reference and addition to the new parent after material reparenting. Its precise per-file sequence is described by `TreeChange` entries returned in partial results: publish new references, publish the material item's parent change, remove old references. The shared recovery-bookkeeping clarification also freezes every affected reference in the tree-update alternative's required `tree_references:ScopeTreeReferenceChange[]`, using `{parent_scope_id,child_scope_id,before,after?}` with the same creation/deletion semantics as HostTreeReferenceChange, but no machine-local checkout path. Parent hosts are resolved under the held routing lock. This covers multiple stored descendants of a reparented implicit item without widening continuation to newly discovered work. The outer step and tree_change.step agree and count each planned file publication; the returned TreeChange.step remains the 0–3 phase (new references, material parent, old-reference removal). During interruption diagnose conflicting ancestry rather than activate either competing tree. Such a multi-file relation/update uses `StartProgress` with optional `tree_change:{item_id,operation:item_update|relation_add|relation_remove,parent_before:ID|null,parent_after:ID|null,old_parent_scope_id,new_parent_scope_id,item_before:Hash,item_after:Hash,step:integer>=0}` and no new run (the `new_run_id,run_created_at,child_before` fields are absent in this alternative). The approved exact-edge clarification requires `operation`, `parent_before` and `parent_after` in every TreePlan; null means no material parent, never the virtual root string. Record the original operation and exact before/after parent item IDs before publication, independently of the nearest stored parent scopes. Continue only through that same item update/relation operation with `continue_id`, exact desired parent/edge and unchanged expected sources. Relation removal must address parent_before and addition must address parent_after, even when the material step is already installed; an unrelated relation kind or operation cannot reuse the plan. This is scope-tree maintenance, not implicit relocation or wisp transfer. All changed material descendants' routing must remain resolvable and prospective graph valid; if new parent would change a surviving dedicated scope host, refuse and require separate host transfer first.

`IgnoreChange` is exactly `{before:Snapshot,after:Hash}` for the fixed primary checkout's root `.gitignore`. Root StartProgress requires it; non-root start/tree variants prohibit it. Generate the deterministic append-only housekeeping result internally, capture its hash before publication and preserve original bytes/rules. Continue only with unchanged expected source/installed result and the frozen run/anchor. No caller-provided arbitrary path/bytes, generic configuration editor or retry receipt is added. Root initialization's pending plan blocks healthy execution even after the anchor step; remove it only after verified ignore and directory postconditions. See [[DES-REPOSITORY-ONBOARDING]].

### 4.2 Host transfer, promotion and disposal rules

`scope host` establishes a dedicated boundary after external preparation of an identical destination subtree; if it is already identically hosted, unchanged. `relocate` transfers a known authoritative dedicated boundary or an implicit material subtree into a dedicated boundary at destination. `adopt` activates an identical externally copied scope at a destination by the same validation/transfer protocol; it does not import arbitrary lost/old claims. `select_authority` explicitly resolves multiple readable identical declaration candidates using the expected inspected inventory and the locked declaration fingerprints. All require `expected_inventory:Hash` from current inspection; changed bytes/candidates fail before intent publication. All candidates to be deactivated must be readable and source-comparable. Missing old source fails `source_unavailable` until externally recovered. Divergent copies fail `conflict`; never choose newest or acknowledge away unverified ownership. A destination must be a Git-inventoried checkout of the same common directory. No Work command commits, merges, copies scope data or removes a worktree. Destination validation verifies item/source graph, scope IDs, continuing run IDs, session/claim/end/handoff bytes and inherited transferred children. Retain all current identities and endings. If any affected current claim exists, `executors_quiescent:true` is required on initial and continued calls; this is caller attestation that executors are paused/stopped, not Work process control. Even with no claims, file fingerprints and source comparison are mandatory. Hosting is the only changed authority; parent references contain no paths to rebind.

Promotion requires no current item claim, active or retained terminal owner run, a scope-resolved material destination with no competing item and a valid prospective graph. Same ID/state/body/relations bytes are copied exactly. The material destination follows material ancestry/nearest host, not merely the wisp home. Source deletion is last. After interrupted destination publication, only matching progress may reconcile copies; normal duplicate-ID diagnostics remain outside that plan. Continued promotion refuses changed bytes or a newly detected claim. Once progress is removed, another promote of a material item is `invalid_argument`, not a permanent receipt. Structural references remain resolvable; no handoff or parent edge is rewritten.

Run disposal targets one **terminal** run, including its owned items/sessions/claims/endings/handoffs; it does not sweep other rounds or child scopes. Scope disposal targets all run histories owned by the selected scope and stored descendants; inherited ancestor runs are outside the set. Active non-root targets require explicit `abandon_active:true`; end bottom-up before deletion without recording material success. Root's active standing run cannot be disposed: rotate first, and dispose only identified old root runs with run disposal. Scope disposal at root refuses while it would include the standing round. Already-absent run without a progress record is `not_found`; an existing empty eligible scope returns unchanged. These operations validate the full plan before first deletion and again before each continuation. Refuse current claims on deletion targets, current claims of deleted named identities in any run, and any surviving item relation to a deleted wisp (all four relation kinds, even already-done dependencies). Report blockers, never silently erase them. Surviving handoff destinations/history are nonstructural audit addresses, not retention gates; they may subsequently report missing targets. Remove only frozen matching files, never broaden a retry to newly discovered work. Surviving material files, digest extensions and hosting overrides remain. Disposal of the selected terminal round replaces its non-root boundary with `mode:"ended"` before deleting its manifest; retain that anchor/reference as an explicit namespace barrier. Only a later fresh start or `run inherit` can resume execution. Remove a dispensable inheriting anchor/child reference only if no history, ended barrier, dedicated material hosting or stored child boundary needs it. Dedicated material hosting is never removed by disposal. External checkout removal requires separately retained/merged material content and validated host transfer, and is not a Work operation.

### 4.3 Other bounded publication contracts

Material CRUD/repair use [[DES-DURABLE-OPERATIONS]] one-file result/conflict/recovery rules, with authoritative routing and ownership checks replacing old physical mutation selection. Like every other writer, material CRUD follows [[DES-FILE-PUBLICATION-LIFECYCLE]]; ordinary verified artifact cleanup returns item `recovery_path:null`, while repair and unresolved publication expose only surviving recovery paths. Unknown legacy/orphan artifacts require explicit caller resolution, not age-based deletion. Broadening this common policy adds no generic recovery operation or wire shape. Misnamed-file repair's canonical publication/archive retry remains exact-byte guarded and inspectable. Invalid candidate/input publishes nothing. Repair can reduce existing diagnostics but introduce none, and cannot bypass terminal-wisp restrictions or claim authorization. Read-only physical raw inspection remains available; repair is always authoritative.

Template expansion allocates all IDs in memory, validates complete rendered prospective graph and destinations, then creates final item documents in local-key order and updates affected existing authored files in canonical path order. Each material destination follows prospective parent ancestry and nearest host (parentless defaults to primary); each wisp must resolve by **declared parent edges** into the explicit/effective target run, including root parentless wisps. A supplied `root` is only a template endpoint, not an automatic parent or an inferred child-run root. Version-1/2 rendering and hint defaults remain unchanged. No write occurs during preview; with no execution target, preview may return `destination:null` for wisps and symbolic graph validation, explicitly `placement_validated:false`. Expansion must resolve/validate all destinations and active run before writes. It creates no run implicitly, no application entity/member list/rollback/idempotency key. Returned failures list allocated key/ID mapping and known created/updated files; a crash may lose the in-memory mapping, so inspect the ordinary files. Caller cleanup/repair then fresh retry allocates new IDs, not deduplication. Never advertise partial graph as claimable.

Close/release with optional outgoing handoffs validates identity, destinations and full intended writes **before** first message. Publish messages in input order, then item completion (close only), then claim ending if current, then any now-drained retiring session's lifecycle update. Returned errors include saved message IDs, published item state and whether ending may have published. Inspect uncertain paths, then retry without already-saved messages; no replay/deduplication promise. Release/recovery remains available for invalid/missing item source and does not mutate it. Reassignment's end-before-new-acquisition gap is visible. Ending/rotation/disposal/promotion/host transfer use only their exact operation-specific progress and `continue_id`; supplying a mismatched operation ID/options is `conflict`. Deleted progress means no retry receipt: inspect actual sources/results, do not blindly repeat a command that would mean a new operation.

## 5. CLI grammar and MCP input matrix

## 6. Structured results and transport

With `--json`, write exactly one UTF-8 JSON object plus newline on stdout: `{ok:true,result:Result}` or `{ok:false,error:Error}`. JSON failures do not also print human stderr. Help/version are successes `{help:string}` / `{version:string}`; human help/version need not use that envelope without --json. Human failures use stderr and the same exit codes. No placeholder success for unsupported commands.

`work mcp` negotiates MCP `2025-06-18` via newline-delimited JSON-RPC 2.0 stdio, tools capability only, no resources/prompts/watches. Tool success is `{structuredContent:Result,content:[{type:"text",text:JSON(Result)}],isError:false}`; domain failure is `{structuredContent:{error:Error},content:[{type:"text",text:JSON({error:Error})}],isError:true}`. Initialize/ping do not initialize Work execution. Unknown methods/tools use JSON-RPC -32601/-32602, malformed protocol requests -32600/-32700, before initialization -32000. Tool argument/domain errors use the shared error, not protocol transport success disguised as a domain pass. `tools/list` must advertise exactly the catalog operations and closed required/optional schemas; no hard-coded beta.1 tool count applies.

All result fields are required unless absent from the catalog schema’s required list; absence observations use explicit null. All mutable result shapes include `changed:boolean`, true when any domain entity/authority changed, false for validated unchanged calls. No unchanged return hides an error/partial write. Common `ReadContext` fields are `view`, `authoritative:boolean`, `execution:ExecutionInspection`, `diagnostics:Diagnostic[]`. Successful reads may expose unavailable contextual evaluation as null with diagnostics; graph-invalid `executable`/`effective_done` are null. Successful mutation/selection needs applicable complete prerequisites and source reload; post-publication reload failure is an error with partial evidence.

## 7. Typed failure matrix and no-write rules

`Error` requires `code,message`; optional fields are `diagnostics:Diagnostic[]`, `item_id,claim_id,run_id,scope_id,operation_id`, `path`, `candidates:HostCandidate[]`, `blockers:Blocker[]`, `recovery_paths:Path[]`, `partial:Partial`, `publication`, `errno:integer`, `remaining_paths:Path[]`, `published_item:PublicationEntry`, `previous_source_path:Path`. Omit unavailable optional fields; do not fill invented values. Ownership conflicts expose conflicting claim IDs through `claims:ClaimView[]`; host ambiguity exposes actual candidates. Semantics are shared across CLI/MCP.

| Codes | CLI exit | Meaning / affected operations |
| --- | --- | --- |
| `usage`, `invalid_argument` | 2 | Syntax/schema/mixed identity/selector/attestation/unsupported target; every operation; no writes |
| `not_found`, `ambiguous_id` | 3 | Missing identity/continuation, ambiguous item prefix; never choose one |
| `invalid_source`, `invalid_candidate`, `invalid_format`, `unsupported_format`, `obsolete_execution`, `coordination_unavailable` | 4 | Invalid whole existing graph, prospective graph, envelope/version, obsolete shared/local execution detected, unavailable initialized coordination; inspection may report as data, scheduling/mutations refuse |
| `already_exists`, `conflict`, `storage_busy`, `unsafe_path`, `host_missing`, `host_ambiguous`, `source_unavailable`, `transition_pending` | 5 | Duplicate edge/competing publication/lock contention/unsafe path/authority loss or ambiguity/pending bounded transition; no stale fallback |
| `claim_conflict`, `stale_claim`, `not_ready`, `run_conflict`, `run_not_current`, `session_conflict`, `session_not_active`, `context_change_claimed`, `wisp_run_mismatch`, `reference_blocked`, `run_unfinished`, `descendant_run_active`, `claims_present` | 5 | Exact domain guard failed with IDs/blockers/diagnostics; no release, rebind or implicit lifecycle success |
| `unsupported_project`, `io` | 1 | Non-Git/bare checkout, filesystem/permission/output failure. Post-publication IO retains partial/recovery evidence |

All operations inherit applicable discovery, argument, source/version, authority, conflict/IO errors; the catalog lists additional operation-specific guards. Read-only diagnosis of uninitialized/missing/invalid content returns diagnostics where a useful inspection exists; inability to access the selected Git project or deliver a result is an error. Ordinary material inspection/CRUD and material-only template planning do not require execution init, but cannot ignore detected obsolete execution/uncertain ownership for mutations. Execution-consuming operations fail uninitialized as `coordination_unavailable`, not implicitly create a root run. Pure available material reads show execution state/diagnostics and null ownership/context when unsafe to resolve, never ready-to-dispatch proof. `item_ready` requires a valid graph and certain coordination when execution exists; before execution init it may list graph-ready material items with `execution_state:uninitialized` and no claims, which is not claim authorization. An ended/material item can be inspected or edited but not acquired until explicit fresh execution/inheritance resumption.

Invalid CLI syntax, field types, conflicting/mixed inputs, unsupported versions and candidate/guard rejection publish **no domain or progress files**. Locks may be opened only after syntactic validation; no lock/bootstrap write before input/candidate checks. If initial execution initialization creates coordination files then cannot publish its first plan, report these known paths as partial IO, not invalid-input success. Candidate/guard checks all precede intent publication. Detected external source changes immediately before any protected write refuse that write; earlier successful files remain in partial evidence. `storage_busy` is explicit contention, not no eligible work. No code promises safety from arbitrary undetected deletion of every ownership file or an uncooperative external Git rewrite.
