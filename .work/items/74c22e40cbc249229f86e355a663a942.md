## Scope

Prepare a separately reviewed release candidate after the first usable CLI/MCP item loop is delivered. This item is outside the implementation aggregate and depends on it. It does not make that aggregate wait for publication or claim the entire initial product scope is complete.

Follow [the delivery and release conventions](../../docs/delivery.mara.md). Resolve the version, license, package identities, installation channels, and supported hosts explicitly. Complete real artifact and CLI/MCP smoke coverage for the chosen distribution. Prepare the version and generated CHANGELOG.md in a dedicated release PR; merging it intentionally starts release verification.

Confirm repository/environment protection and any registry publishing prerequisites. Follow the verified candidate through authorized publication and record the immutable source revision, tag, artifacts, workflow results, and public-install evidence. This issue is not blanket authorization to merge, approve protected publication, or publish externally.

## Candidate selections

- First candidate version: `0.1.0-alpha.1`, on the `0.1.0` release line.
- License: `MIT OR Apache-2.0`, chosen explicitly for the first release.
- Package identities and three supported hosts: use the accepted `ADR-WORK-DISTRIBUTION` contract. Verify the package contents and actual external settings before publication.
- For each of the four npm packages, confirm its trusted publisher matches `convesoft/work` and `release.yml`, has no npm environment-name restriction, and allows direct `npm publish` as used by the workflow.

## Acceptance criteria

- The prerequisite milestone is complete with implementation and merge evidence.
- The release is scoped as a usable alpha; README and release notes distinguish delivered features from later coordination, templates/runs, sessions/workspaces, handoffs, and finalization work.
- The selected version is consistent across the source and packages, and git-cliff reproduces the committed changelog from the release history.
- Licensing, package names, installation channels, and supported platforms are settled and recorded in repository guidance.
- The release workflow passes source checks, Mara schema/project validation, artifact inspection, and real packaged CLI/MCP smoke tests for every declared host at one captured main revision.
- GitHub release protection and any registry trust are verified as actual server-side settings before publication.
- Authorized publication produces an annotated tag at the verified revision and matching published artifacts. Public installation and CLI/MCP smoke checks succeed for the released version.
- Publication evidence and limitations are recorded. Failed or partial publication leaves this item open with retry context; merging the preparation PR alone does not complete it.
