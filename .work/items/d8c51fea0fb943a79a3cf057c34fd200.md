## Scope

Define separate run manifest, wisp and active execution-state files, one-run-per-root behavior, and ordinary template expansion. Extend the template format/preview with a per-item material/wisp selector and settle compatibility before coding. One template may mix both: material items go to the selected checkout `.work/items/`, wisps to run `items/`; material-only planning requires no run. Create no application records, retry keys or transaction engine. Integrate active-run state into normal inspection/readiness while keeping durable definitions checkout-specific.

## Acceptance criteria

- One root item has one shared run; duplicate start identifies that run or reports a clear conflict.
- Each run and wisp has its own authoritative file; active-run state has an explicit authoritative representation without duplicating durable bodies or embedding all entities in the manifest.
- Mixed-template CLI/MCP creation places material items and wisps correctly, preserves ordinary relations, and returns permanent IDs mapped from preview keys. Material-only expansion creates no run.
- Validate prospective inputs/graph before writes. On an injected failure after three of five creations, preserve/report known created files; the caller can inspect, remove the partial result and retry. No application record, rollback or deduplication guarantee is introduced. Ordinary graph diagnostics remain applicable.
- Linked worktrees inspect the same active execution state, which takes precedence over recorded state for normal queries. Bodies/relationships remain selected locally and recorded versus effective state is explicit. Reads do not rewrite durable files; CLI/MCP and restart tests cover the loop.
