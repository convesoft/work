## Scope

Add repository-wide claim, inspect, release, and reassignment operations over the shared coordination identity. Emit a new `claims/<claim-id>.yaml` for each acquisition, retain prior claims, and check current ownership under the shared lock using claim ID plus session identity. No separate secret token or token store. Use the specified acquisition/ending files and operation schemas in Mara; do not infer that retiring a claim stops an external executor.

## Acceptance criteria

- Concurrent claim attempts for the same item across linked worktrees yield one owner and a clear conflict.
- Claim acquisition consumes the foundation's coordination-availability status and refuses ownership when storage is uninitialized, damaged, unreadable or incomplete, including pending recovery. Prove this through real CLI/MCP claim requests without treating unavailable storage as an empty ownership set.
- Claims carry agent/session identity and can be inspected, explicitly released, or reassigned with explicit recovery context. New ownership never repurposes an old acquisition. Current selection does not rely on caller timestamps.
- The same session reacquiring the same item gets a new claim ID; former claim/session pairs fail owner operations after release, completion, reassignment or storage recreation.
- Stale or detectably lost/corrupt ownership is visible and explicitly recoverable without automatic expiry or mandatory heartbeat. Unreadable/malformed claims never count as unclaimed. Recovery rejects former claim/session authorizations; notifications are not required for exclusion.
- Readiness explains ownership restrictions; CLI/MCP behavior and crash/restart tests agree.

## Mara contracts

`REQ-CLAIM-EXCLUSION`, `REQ-CLAIM-RECOVERY`, `DES-CLAIM-CONTEXT`, `DES-FILE-COORDINATION`, `DES-ENTITY-LIFECYCLES`, `RISK-STALE-COORDINATION`. Exact interfaces: `DES-CLAIM-API`, `DES-EXECUTION-IO`, `DES-CONTEXT-API`. Follow [the prepared handoff](../handoffs/beta-execution.md); new material decisions still require Mara updates before code changes.

## Implementation boundary

The claim file/ending and operation contracts are settled in `DES-CLAIM-API`; use the common IO/resolved-view boundary in `DES-EXECUTION-IO`. Completion wiring, basic workspace registration/binding, shared lock integration and adapters are owned by the main session. No run implementation or claim-next dependency is needed for the first durable-item claim loop.
